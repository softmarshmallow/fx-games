FX Games/Docs/Glossary

Glossary

The words FX Games uses for its parts, the words it retired, and the persisted strings that keep an old word because changing them would change an identity.

Terms

TermMeaning
Grida FXThe engine every workflow runs on (gridaco/fx), a submodule at third_party/fx: the workflow file, planning and prices, the store, the run record, retries, the built-in node types and the provider adapters. FX Games runs it as uv run python -m grida.fx and imports it as grida.fx.
node typeWhat a step uses: an FX built-in (fx/<type>@1) or a type of the workflow's own (./nodes/<file>.py#<function>, an @node body taking Ctx). The catalog lists each leaf step of a workflow file as one type, <folder>/<step path>, titled by the step's title: (a reader label, kept out of cache keys); the identity golden (tests/contract/fixtures/workflow-identity.json) pins the type identity FX resolves its uses: to.
nodeOne step instance in a plan, with its identity.
componentA package under src/fx_games/components/: contracts, prompts, validators and deterministic processing that a workflow's node types call. It never runs alone and never imports a workflow.
workflowOne folder under src/fx_games/workflows/ that makes one kind of deliverable: its workflow file (workflow.yaml) beside its own fx.yaml and fx.lock, workflow.py, workflow.toml, page.mdx, contract.md, its node types and, where it has them, example.py (its example importer) and inputs/. The root fx.yaml finds it by its id, so python -m grida.fx plan <id> and run <id> plan and run it; its kebab-case id is that word, the site's slug and the docs path.
projectA folder with an fx.yaml: where its runs (runs:) and store (cache:) go, the routes its calls take (routes:) and, for the root project, where workflows are found by id (workflows:). Each workflow home is one, and so is each game folder that builds with FX.
stepA top-level step of a workflow file, with its title: and description:, as readers see it. Every leaf step under it is one node type, and every node type sits in exactly one step.
inputA folder a run reads. A workflow's committed sample inputs live in its inputs/<name>/.
runOne execution folder. A chain, such as a take and then its finish, is several runs.
exampleA frozen export of real runs (example.json, figures.json and media/), pinned by sha256 in its owner's manifest and made by a workflow or a game. It is the only result the site shows. An example made with an earlier version of its workflow says so behind a disclosure.
takeOne draw of a step's request. takes: draws several at once, python -m grida.fx reroll draws the next, and pick keeps one in the takes file, <workflow id>.takes.yaml: beside a builder (a game's pipeline/<id>.takes.yaml) or a workflow file whose home is the project you run from, else at the root of the project you run from (the installed workflows, found by id from the root fx.yaml, keep theirs at the checkout root, such as universe.takes.yaml). An audition is a take a person chose, which a run may adopt by digest as a file.
stand-inA function that answers a run's paid calls in a test, offline and for nothing (grida.fx.run(..., stand_in=...)); its answers pass the checks a provider's do, and its records stay apart from real ones.
SDKGrida FX's Python package, grida.fx: a builder (Workflow, plan, run), node types (@node over a body taking Ctx) and stand-ins. FX Games' workflows and every game build are written with it.
run viewfx-games-run-view-v1: fx_games.runview's projection of an FX run folder, which the examples store reads.
catalogThe fx-games-catalog-v1 JSON that scripts/catalog.py writes from the installed workflows and the example store. It is derived and never committed.
siteweb/site, the static landing and documentation, built from the catalog and the example store.
viewerFX's viewer, which uv run python -m grida.fx start --open opens: the local, read-only canvas over a project's plans and runs. FX Games keeps none of its own (decision 0075).

Frozen persisted strings

These keep their old words because they are written into runs, caches or digests. Leave them as they are:

  • the <word>-execution-{graph,event,summary,projection,view} kinds and pipeline-execution-*;
  • the recipe and recipe_version fields of the game documents that carry them, such as The Grain's dialogue scene (dialogue-scene-v8);
  • the @stage-gen/<name> provenance names, the stage-gen tool identity and the stage-gen-headless source of committed media sidecars;
  • the stage-gen/dialogue-scene/... digest domains of The Grain's dialogue scene;
  • the bytes of committed game inputs, comments included, which their package digests pin.

The domain phrases "rig recipe" and "crafting recipe" are unrelated and stay.
